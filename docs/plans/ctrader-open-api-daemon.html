Démon cTrader Open API

Remplacer les deux cBots par un service serveur connecté à l'Open API de Spotware — tracking des trades et rollover guard en 24/7, sans cTrader Desktop ni exécution cloud. Plan du 29/09/2026.

✅ Livré le 01/10/2026 — phases 0 à 5 réalisées, démon en prod (healthy, tracker actif). Le rollover guard reste GUARD_ENABLED=false pendant la période d'observation (phase 4) : le cBot guard local reste en service. Doc de référence à jour : ctrader-daemon/README.md (ce plan est historique).
Pourquoi ce chantier. L'exécution cloud gratuite de cTrader bloque toutes les requêtes HTTP sortantes (seul un WebSocket vers le port 25345 est toléré) : les cBots y démarrent mais leurs appels vers /api/trades sont avalés silencieusement. Constaté en prod le 29/09/2026 — aucun POST /api/trades dans les logs nginx alors que le bot cloud loggait ses tentatives. Les cBots restent fonctionnels en exécution locale (cTrader Desktop ouvert), qui sert de solution de repli pendant toute la durée du chantier.

1. Architecture cible

┌─────────────────────┐   ProtoOAExecutionEvent    ┌──────────────────────── droplet ───┐
│  Serveurs Spotware   │ ─────────(push)──────────▶ │  ctrader-daemon (nouveau conteneur) │
│ live.ctraderapi.com  │ ◀──ProtoOAAmendPositionSLTP│      │ POST/PATCH /api/trades        │
│   :5035 (TCP+SSL)    │       (rollover guard)     │      ▼ (token API existant)         │
└─────────────────────┘                             │  nginx ──▶ app (Symfony)  ──▶ db    │
                                                    └─────────────────────────────────────┘
  • Un seul service nouveau : ctrader-daemon, ajouté à compose.prod.yaml.
  • Il consomme la même API REST que les cBots (mêmes payloads, même token personnel) : aucun changement côté Symfony.
  • Connexion sortante droplet → Spotware : rien à ouvrir sur le firewall.
  • Les deux cBots actuels sont conservés dans ctrader/ comme solution locale de secours.
Décisions proposées (à valider avant la phase 1) :
  • Langage : Python avec le SDK officiel Spotware OpenApiPy (Twisted). Alternative : C# avec OpenAPI.Net pour rester proche du code des cBots — mais Python simplifie l'image Docker et le SDK est le mieux maintenu.
  • Passer par l'API REST Symfony et non par un accès direct à la base : réutilise la validation, l'idempotence par dealId et la logique de calcul déjà testées.
  • Un seul compte suivi (le compte live actuel) — pas de multi-comptes dans cette version.

2. Prérequis OAuth (manuel, une seule fois)

  1. Créer un compte partenaire sur openapi.ctrader.com avec le cTrader ID.
  2. Créer une application : nom, redirect URI (ex. https://trading-tracker.freeddns.org/ctrader/oauth/callback — une page statique suffit, on ne s'en sert qu'une fois pour récupérer le code).
  3. Récupérer client_id et client_secret.
  4. Dérouler le flow OAuth (scope trading) une fois dans le navigateur → access_token + refresh_token.
  5. Récupérer le ctidTraderAccountId du compte live via ProtoOAGetAccountListByAccessTokenReq.

Le tout atterrit dans le .env du droplet (jamais commité — repo public) :

CTRADER_CLIENT_ID=
CTRADER_CLIENT_SECRET=
CTRADER_ACCESS_TOKEN=      # renouvelé ensuite automatiquement par le démon
CTRADER_REFRESH_TOKEN=
CTRADER_ACCOUNT_ID=        # ctidTraderAccountId
TRACKER_API_TOKEN=         # token personnel existant (Mon profil → Token API cTrader)

3. Composant tracker (remplace TradingTrackerBot)

Composant 100 % passif côté broker : il écoute les événements que Spotware pousse (colonne de gauche = ce que le démon reçoit quand le trader agit) et n'écrit que vers l'API REST de Trading Tracker. Il n'envoie jamais le moindre ordre au broker.

Événement reçu (action du trader)Réaction du démon (API Trading Tracker)Équivalent cBot
Ouverture d'une position (ProtoOAExecutionEvent, fill d'ouverture) POST /api/trades (asset, orderType, entryDate, risque, RR initial, SL, entryPrice, targetPrice, volume, ctraderPositionId) Positions.Opened
Déplacement du SL/TP par le trader PATCH — risque recalculé, SL ajouté à l'historique stopLosses (l'API déduplique) Positions.Modified
Clôture par le trader ou par SL/TP (fill de clôture, partielle ou totale) PATCH avec exit: {dealId, price, volume, date} ; closed: true sur le dernier deal — idempotence par dealId conservée Positions.Closed + sync History

Améliorations par rapport au cBot

  • Logs exploitables : chaque appel REST loggé avec méthode, URL et code HTTP.
  • Pas de rattrapage (choix assumé) : le démon est purement événementiel, comme le cBot — une position ouverte avant son démarrage ou un événement manqué pendant une coupure ne sont pas recréés automatiquement ; correction manuelle dans l'app si besoin.

Points techniques

  • Mapping symbolId → nom via ProtoOASymbolsListReq (cache en mémoire), puis même normalisation que le cBot (EURUSD → EUR/USD, suffixes broker retirés) contre la liste des paires supportées — à resynchroniser avec Trade::ALLOWED_ASSETS. Cas particuliers confirmés : GBPNZD → GBP/NZD (comme les autres paires), NAS100 tel quel, et le symbole broker USWTI correspond à USOIL dans l'app.
  • Calcul du risque : distance SL en pips via pipPosition/lotSize de ProtoOASymbol (l'équivalent de Symbol.PipSize/PipValue du cBot — à valider en phase 2 sur des cas réels).

4. Composant rollover guard (remplace RolloverStopLossGuard)

  • Planificateur interne calé sur America/New_York (comme le cBot — l'heure de Paris reste juste toute l'année).
  • 17h00 NY − 5 min : pour chaque position avec SL — pousser le niveau dans stopLosses via l'API REST, puis retirer le SL via ProtoOAAmendPositionSLTPReq. API injoignable → SL laissé en place (le niveau ne doit jamais être perdu).
  • 17h00 NY + 10 min : remettre sur chaque position sans SL le dernier élément de stopLosses. Refus broker (prix a traversé le niveau) → warning loggé, pas de fermeture automatique.
  • Positions non trackées : intouchées, comme aujourd'hui.
  • Avantage sur le cBot : tracker et guard partagent le même processus — plus de risque de double instance ou d'instance oubliée.

5. Garde-fous financiers

Principe : le démon ne peut pas faire perdre d'argent par lui-même.
  • Aucun passage d'ordre, par construction : le code ne contient aucun appel d'ouverture, de clôture ou de changement de volume (ProtoOANewOrderReq, close, etc. ne sont jamais implémentés). La seule écriture broker est ProtoOAAmendPositionSLTPReq (SL du rollover guard) — comme le cBot actuel.
  • Le niveau de SL n'est jamais perdu : sauvegardé en base avant tout retrait ; échec de sauvegarde → SL laissé en place. Au (re)démarrage hors fenêtre, restauration des SL manquants — uniquement sur les positions liées à un trade tracké en base (dernier niveau de stopLosses) ; toute autre position reste intouchée.
  • Le guard n'agit que dans sa fenêtre (17h00 NY ±) : hors fenêtre, le démon ne touche à rien côté broker (hors restauration de SL manquants ci-dessus).
  • Validation intégrale sur compte démo (phases 1–3) avant tout contact avec le compte live, avec comparaison de parité face au cBot local.
  • Mise en live progressive : la phase 4 démarre avec le guard désactivé (flag GUARD_ENABLED=false) — tracker seul, donc zéro écriture broker — puis activation du guard après quelques jours et un cycle de rollover validé en démo.
  • Coupe-circuit trivial : docker compose stop ctrader-daemon arrête tout ; les positions gardent leur SL (le retrait n'a lieu que dans la fenêtre, et un démon arrêté ne retire rien).
  • Risque résiduel inchangé : la fenêtre de rollover sans filet (~15 min), compromis déjà assumé avec le cBot actuel — le démon ne l'élargit pas.

6. Connexion, tokens, résilience

  • Keepalive : ProtoHeartbeatEvent toutes les ~10 s (la connexion est coupée après ~30 s de silence).
  • Refresh token : l'access token expire (~30 jours) → ProtoOARefreshTokenReq automatique ; tokens persistés dans un petit volume (ctrader_tokens) pour survivre aux redémarrages. Échec de refresh = seule vraie panne « silencieuse » possible → erreur remontée à Sentry.
  • Reconnexion : backoff exponentiel + re-authentification + re-souscription aux événements. Pas de rattrapage des événements manqués pendant la coupure (voir section 3).
  • Rate limits Spotware (~50 msg/s) : très loin de notre volume, aucun throttling à prévoir.

7. Déploiement

  • Nouveau dossier ctrader-daemon/ : Dockerfile (python:3.13-slim), code, README.md dédié (conforme à la règle « README par répertoire autonome »).
  • Service dans compose.prod.yaml : restart: unless-stopped, env depuis le .env du droplet, volume tokens, healthcheck simple (fichier heartbeat touché à chaque événement/keepalive).
  • Logs via docker compose logs ctrader-daemon ; cible Makefile prod-daemon-logs.
  • Dev : testable en local contre un compte démo (demo.ctraderapi.com:5035) et l'app sur localhost:8001.

8. Phases

Phase 0 — Enregistrement OAuth toi

Créer l'app sur openapi.ctrader.com, dérouler le flow une fois (guidé pas à pas), remplir le .env du droplet. ~30 min, bloquant pour la suite.

Phase 1 — Squelette de connexion Claude

Démon qui se connecte, s'authentifie (app + compte), maintient le heartbeat, souscrit aux événements du compte et logge tout. Critère : les événements d'un trade démo apparaissent dans les logs.

Phase 2 — Portage du tracker Claude

Mapping symboles, calcul du risque, POST/PATCH/exits. Critère : parité avec TradingTrackerBot sur un compte démo (ouverture, déplacement de SL, clôture partielle, clôture totale).

Phase 3 — Portage du rollover guard Claude

Fenêtre 17h00 NY, retrait/restauration des SL, mêmes règles d'échec que le cBot. Critère : un cycle complet observé sur compte démo.

Phase 4 — Prod en double marche Claude toi

Déploiement sur le droplet branché sur le compte live, cBots locaux éteints (pas de doublons : l'idempotence par dealId protège, mais autant éviter). Observation sur quelques jours de trading réels, dont un passage de rollover.

Phase 5 — Bascule définitive Claude

Mise à jour de la doc : ctrader/README.md (corriger la fausse promesse d'exécution cloud, marquer les cBots comme solution locale de secours), docs/ARCHITECTURE.md et docs/PRODUCTION.md (nouveau conteneur, runbook).

Terminé quand : un trade ouvert depuis n'importe quel appareil (mobile inclus, Mac éteint) apparaît dans Trading Tracker en quelques secondes ; les SL survivent au rollover ; le démon survit à un redémarrage du droplet et à une coupure réseau (reconnexion automatique) ; plus aucun cBot nécessaire.
